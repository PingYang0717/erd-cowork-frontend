# 0015. 樂觀更新與競態的正確性約定

日期:2026-09-04

## 背景

這份文件把先前散在程式碼裡的 `(C-2)`…`(C-5)` 代號收編成正式決策,理由與 ADR-0014 相同:
它們被引用了 6 次、跨 5 個檔案,而倉庫裡沒有任何地方定義過它們。

與 A-* 家族不同的是,C-* 每一條都是**修過的真實 bug**,不是預防性的規範。它們看起來都像
可以「順手簡化」的地方,而每一次簡化都會把原本的 bug 放回去。這是它們最需要被寫下來的
原因——沒有紀錄的話,下一個讀到的人只會覺得這裡寫得囉唆。

## 決策

### optimistic-bubble:比歷史長度,不比最後一則文字

樂觀泡泡在使用者送出的當下就上螢幕,並記下**當時的歷史長度**(`atLength`)。泡泡的抑制
條件是「重取回來的歷史長度已經超過 `atLength`」——那個增長就是重取把訊息帶回來了。

**不可以改成比對最後一則歷史文字。** 連續送出兩則相同的訊息時,前一則相同的訊息會讓
文字比對誤判成「重取已經落地」,第二顆泡泡因此被錯誤抑制,使用者會看到自己打的字消失。
長度比對不受重複內容影響。

配套:執行結束時**刻意不呼叫 `setPending(null)`**。成功路徑不需要(推導本身會抑制),
失敗路徑則絕對不能有——失敗時歷史沒有東西可以承接,清掉等於讓使用者自己打的字連同錯誤
一起消失。

### stop-is-a-no-op-when-idle:stop() 只在串流讀取中才作用

`stop()` 只在串流正在被讀取時才有效果。對一個閒置的 hook 沒有東西可以停——如果這時候
還去標記 `stopped`,畫面會出現一顆「已停止」的幽靈泡泡,而它旁邊根本沒有發生過任何執行。

### artifact-scoped-offers:每個 artifact 範圍的寫入都要驗 id

修復提議屬於「某一個 session 裡的某一個 artifact」。所有 artifact 範圍的 mutation 都必須
檢查 id 再寫入:A 的修復如果在使用者已經切到 C 的提議之後才回來,不可以把 A 的狀態寫到
C 身上。

第二個壞掉的 artifact **要進佇列,不能丟掉**。先前的行為是第一個提議還在時就把第二個丟棄,
結果那個 artifact 完全沒有機會被修復;現在它排隊等第一個消失後浮出。

### run-in-progress-wins:agent 回答中,artifact 的錯誤不進對話

Artifact 在 iframe 裡丟出錯誤(postMessage `erd-artifact-error`,或 MCP bridge 的失敗)時,
如果 agent 正在回答(`isRunStreaming`),這份回報**直接丟掉**,不顯示、也不排隊。

**為什麼。** 這時候面板上的 artifact 只有兩種:正在被這一輪寫到一半的那一份(半成品跑起來
本來就會出錯),或是這一輪即將取代的上一份。兩種都不值得在對話裡插一張「要不要修?」——
使用者已經在跟 agent 談這件事了,新的對話優先。

**為什麼不排隊。** 佇列是給「第一個提議還在、第二個 artifact 又壞了」的情況(上一節):
那個 artifact 沒有別的機會被修。這裡不是:等這一輪結束,畫面上的 artifact 已經不是報錯的
那一份;排隊等到的提議會指著一個不在畫面上的東西。如果新的那一份也壞,它會自己再回報一次。

### failed-run-hands-over:失敗的執行,歷史接住了就交棒

執行失敗留下來的那顆泡泡,只活到「重取把這一輪的回覆帶回歷史」為止。條件跟上面同一個形狀:
`messages.length` 超過 `atLength`,而且歷史的尾巴是一則 AI 訊息——這一輪到家了。

**為什麼不是一直留著。** 後端回報失敗時,通常也把 agent 自己對這次失敗的說法存成一則訊息;
那則訊息就是使用者需要的說明,而且步驟摘要的紅色 ✗ 就在它旁邊(`stepsJson` 有存,重整還在)。
泡泡繼續開著等於同一件事講第二遍,而且是用後端寫給 log 看的字講的(ADR-0016)。更糟的是那條
紅字只活在 live state,重整就消失——留下的反而是三個訊號裡最短命的一個。

**但歷史沒接住的時候一定要留。** 串流根本沒開起來(POST 直接非 2xx)、或送了 ERROR 而後端
沒存下任何訊息,歷史就沒有任何一列在講這件事,泡泡是使用者唯一能看到的交代。

這一條跟 stop 的交棒是同一個道理:畫面上的東西必須等於歷史裡的東西,否則現在看到的跟重整
之後看到的是兩回事。

## 後果

- 6 處 `(C-n)` 改寫成 `(ADR-0015 §<小節名>)`。
- 這五條都有測試在盯:`optimisticBubble.test.ts` 直接測「連送兩次相同文字」這個情境,
  `useAgentStream.test.ts` 測閒置時 stop 的無作用,`useRepairOfferStore.test.ts` 測
  跨 artifact 的錯寫、佇列與回答中的丟棄,`StudioPage.repair.test.tsx` 測回答中的錯誤
  不進對話,`StudioPage.error.test.tsx` 測失敗執行的交棒與不交棒兩種情況。
  要驗證這些約定還活著,跑這五個測試檔就夠。
- 代號家族沒有 C-1,因為那份個人清單從 C-2 開始編。之後要新增約定直接在這份 ADR 加一個
  小節,不要再開新的代號體系。
